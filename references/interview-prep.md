# Interview Prep Playbook

The reference for **C. PREP**. Two deliverables — a **prep kit** (a written brief)
and a **mock interview** (an interactive loop) — plus the round-by-round emphasis
that shapes both. The governing principle is **continuity**: prep emphasizes the
exact strengths the application positioned on and defends the exact gaps it logged,
so the user stays consistent with what got them the call. Never generic advice.

The never-fabricate rule applies here in full. In prep you are helping the user
present *their real* material as well as possible — sharpening, reordering, and
framing true experience. You never invent a story, metric, or credential to make an
answer land, and when the user fumbles, you help them reshape something real, not
substitute a better fiction.

---

## Inputs — gather before you start

Pull as much of this as exists; prep degrades gracefully if some is missing.

- **The JD** — ideally the original posting. In the application chat it's already in
  context; in a fresh chat, ask for it.
- **The strategy/tailoring notes** — the positioning angle, the strengths surfaced,
  and the ATS hard-gaps recorded in the RUN report. This is the spine of the kit.
- **`fact-pack.md`** — signature stories (incl. the "deviated from process" story and
  a failure/conflict story), metrics, elevator pitch, differentiators, honest gaps.
- **`profile.json`** — comp target/floor, work auth, logistics answers.
- **`resume_<company>.md`** — the tailored resume, if still around, shows exactly
  which lines were emphasized for this role.
- **The round** — recruiter / hiring-manager / panel / portfolio / technical / final.
  Ask if unclear; default to hiring-manager behavioral.

If there's no library yet, prep can still run thin off just the JD and whatever the
user tells you — but say the kit will be sharper after onboarding.

---

## The prep kit — the eight parts

Assemble these from the inputs above. Keep each tight; the whole kit should be
phone-readable before an interview, not a research dossier. Deliver as chat text by
default; offer a file only if the user wants something to keep.

### 1. Company & role refresher
What the company does in plain terms, who it serves, and how this role fits. If you
have web access and there may be recent news (funding, launches, leadership changes,
layoffs), do a quick check so the user isn't blindsided — but don't pad with trivia.
Then a plain read of what the role **actually owns and is measured on**, decoded from
the JD's responsibilities (not its adjectives).

### 2. Your angle
The one-line positioning the application led with, restated as the through line to
hold across every answer. Everything else in the kit hangs off this.

### 3. Strengths to emphasize
The 3–5 strongest alignments between the user's background and this role. For each:
the claim, the proof point (a real metric or outcome from the fact pack), and the
story to reach for if pressed. These are what the user steers toward.

### 4. Gaps to manage
The honest gaps logged during the application, plus any new ones the JD implies. For
each, a **prepared, non-defensive framing** — acknowledge plainly, bridge to adjacent
real experience, show the learning curve is short. These are the "questions you're
afraid of." Flag them as the highest-priority rehearsal targets. Never coach the user
to bluff a gap — coach them to handle it honestly and move on.

### 5. Story bank, mapped
Take the signature stories from `fact-pack.md` and **map each to the competencies
this role screens for**, so the user knows which story answers which kind of question.
Cover at minimum: a leadership/influence story, a conflict or disagreement story, a
failure/what-I'd-do-differently story, and the "deviated from standard process"
story (very commonly asked). Note the one-line STAR spine for each (Situation →
Task → Action → Result) so they're recallable under pressure.

### 6. Predicted questions
The behavioral and role-specific questions **this posting** is most likely to
generate — derived from its responsibilities, its seniority, and the gaps — each with
a one-line angle and which mapped story to reach for. Include the obvious openers
("walk me through your background", "why this company", "why leaving") plus 4–6
role-specific ones. This is not a generic 50-question bank; it's the short list most
likely to actually come up.

### 7. Questions to ask them
Tiered by interviewer, because asking the right person the right thing reads as
seniority:
- **Recruiter** — process, timeline, comp range, what the team is solving for.
- **Hiring manager** — what success looks like at 90 days / 1 year, the hardest part
  of the role, how decisions get made.
- **Skip-level / exec** — strategy, where the team is headed, what would make this a
  great hire a year from now.
Include 1–2 questions that quietly surface **red flags** (why the role is open, how
the last person in it did, how the team handles disagreement).

### 8. Logistics & comp
The user's target/floor from `profile.json`; how to **deflect an early comp
question** (defer to range, redirect to fit) without stonewalling; and any format
specifics they've shared (who they're meeting, how long, remote/onsite).

---

## Round-by-round emphasis

The round reshapes which parts matter most:

- **Recruiter screen** — lead with parts 2 (angle), 7 (comp/logistics questions), and
  the tight version of 1. Tighten the elevator pitch. Comp positioning matters here
  more than story depth.
- **Hiring-manager / behavioral** — the core round. Parts 5 (mapped stories) and 4
  (gap defense) carry it. Drill STAR delivery.
- **Panel / cross-functional** — emphasize breadth and working-style stories; prep a
  stakeholder-management and a cross-team-conflict story. Different panelists probe
  different competencies — map stories to each likely interviewer.
- **Portfolio / case review** (design, eng, PM) — which work to lead with and why,
  how to narrate decisions and tradeoffs, and how to handle "what would you do
  differently." Pick 2–3 pieces that map to this role's problems; rehearse the
  narration, not just the artifacts.
- **Technical / take-home** — scope expectations, what "good" looks like, and how to
  talk through tradeoffs out loud. Prep the user to state assumptions and reason
  aloud rather than chase a single right answer.
- **Final / executive / skip-level** — vision, trajectory, culture-add, and smart
  upward questions (part 7, exec tier). Less "can you do the job," more "where are
  you taking it and do we want you in the room."

---

## The mock interview loop

Run it like a real interview, not a quiz.

1. **Set the frame.** State the round you're simulating and who you're playing ("I'll
   be the hiring manager for the Staff PM role"). Tell them you'll ask one question
   at a time and give feedback after each, and that they can tap out anytime.
2. **One question at a time.** Ask, then **stop and wait** for their answer. Never
   stack questions or answer for them.
3. **Feedback after each.** Brief and specific: what landed, what to tighten, whether
   they reached for the right story, whether a STAR answer had a real Result. Praise
   what's genuinely strong; don't manufacture praise.
4. **Calibrate to the round** and lean into the **gap questions** — those are where
   reps matter most. Pull from the predicted-questions list; escalate difficulty as
   they warm up.
5. **Hold the line on truth.** If they fumble or start inventing, stop and help them
   rebuild the answer from their *real* material. A polished lie rehearsed here
   detonates in the room.
6. **Wrap.** After ~6–10 questions (or when they call it), give a short overall read:
   strongest answers, the 2–3 highest-leverage fixes, and any story that still needs
   sharpening before the real thing.

Keep your interviewer turns short — the user should be doing most of the talking, as
in a real interview.

---

## Closing the session

Point the user to whichever deliverable they haven't used ("want to run the mock
now?" / "want the written kit to take with you?"). Remind them prep is sharpest when
run **from the application chat**, where the JD and strategy are already loaded. If
the library was thin where it mattered (no failure story, a sparse story bank, gaps
with no prepared framing), name it so they can enrich `fact-pack.md` before the next
round — every prep session is a chance to make the library better.

# The Debrief — learning from the real interview

Prep gets the user ready; the debrief is how the kit gets *better* at preparing them.
After a real interview, it grades what actually happened against the prep kit and feeds
the result back into the library, so every interview sharpens the next one. This is the
highest-value signal the kit ever receives — real performance under real pressure, not
rehearsal.

## The hard input requirement: a transcript, or nothing

The debrief runs on a **written transcript** of the actual interview. It does **not**
run on the user's memory of how it went. A from-recollection recap is too lossy and too
biased by the user's own in-the-moment impression — people misremember which questions
were asked, overweight the one answer that felt awkward, and forget the three that
landed. Grading that recap would produce confident, wrong feedback, which is worse than
none. So: **no transcript → no debrief.** Say so plainly, and point them at the capture
setup below so they have one next time. Don't offer a memory-based substitute.

**Any accurate plain-text transcript works** — Meetily (recommended below), Otter,
Fathom, the call platform's own captions (Zoom / Google Meet / Teams export), or a clean
manual transcription. What matters is fidelity to what was actually said, not the tool;
speaker labels help but aren't required. The user pastes the text in (or saves it to a
file).

## Consent tier — check this before recommending recording

Recording a call captures the other party's voice. Whether the user needs the other
party's consent depends on where the recording takes place. Check
`profile.json → interview_recording.consent_tier` before surfacing any recording
recommendation:

- **`one_party`** — only the user's own consent is required (most US states, including
  CO). Recommend Meetily freely; the caveat is a single line the first time, then drop
  it.
- **`two_party`** — all parties must consent before recording begins. States in this
  category include CA, CT, FL, IL, MD, MA, MI, MT, NH, OR, PA, WA (and equivalents
  elsewhere — verify locally). **Almost never raise recording unprompted** when this
  tier is set. If the user brings it up or asks, surface the caveat first and leave
  the choice entirely with them: *"[State] requires all parties to consent before you
  record. If you disclose at the start of the call and get agreement, a tool like
  Meetily works well — but that disclosure is yours to make."* Do not push or repeat.
- **`null` (unknown)** — ask before recommending. One question: *"What state (or
  country) are you recording in? That affects whether you can record without disclosing
  it."* Once they answer, apply the appropriate tier above and save `consent_tier` to
  `profile.json → interview_recording.consent_tier`.

This is the user's legal call to make, not the kit's — flag it; don't police it.
Don't refuse to process a transcript the user brings regardless of tier.

## Capturing the transcript — Meetily and alternatives

**Any accurate plain-text transcript works** — Meetily (recommended for one-party
users below), Otter, Fathom, the call platform's own captions (Zoom / Google Meet /
Teams export), or a clean manual transcription. Speaker labels help but aren't
required. The user pastes the text in (or saves it to a file and references the path).

### Meetily (recommended for one-party-consent users — free, discreet, local)

When `consent_tier` is `one_party` and the user doesn't already have a tool set up,
recommend Meetily: a free, open-source (MIT) notetaker that records and transcribes
**locally on the user's own machine** with Whisper/Parakeet — no bot joins the call,
no audio leaves the device, no account required. It's recommended because it's discreet
(nothing shows up on the interviewer's end) and private (transcript stays on the user's
machine). Two capture modes:

- **Video call (Zoom / Google Meet / Teams):** Meetily taps **system audio**, so both
  the user and the interviewer come through cleanly from the same stream that reaches
  the speakers. No participant appears in the call. This is the high-fidelity path.
- **Phone call:** a phone call's audio doesn't route through the computer, so put the
  call on **speakerphone** and let Meetily capture it through the laptop **mic**. The
  user's voice is clean; the interviewer's voice is whatever the phone speaker plays
  into the room. Practical tips: quiet room, phone volume up, phone close to the laptop
  mic, and **run a 60-second test recording beforehand** to confirm the speaker side
  transcribes legibly. Whisper handles speakerphone audio reasonably but is more
  sensitive to a noisy room than a direct stream.

Either way the user exports the transcript as plain text and pastes it into the chat.
Nothing is uploaded anywhere. When `consent_tier` is `two_party`, skip this
recommendation unless the user explicitly asks; apply the caveat above first.

## Running the debrief

With a transcript in hand:

1. **Anchor to the prep kit.** Pull the predicted-questions list, the mapped stories,
   and the logged gaps from the prep session (or reconstruct them from the JD + library
   if this is a fresh chat). The debrief's whole value is grading *against what you
   prepped*, not generic critique.
2. **Walk the transcript and assess:**
   - **Coverage** — which predicted questions actually came up, and which real questions
     the prep *failed* to predict (these are gold for next time).
   - **Answer quality** — for the questions that mattered, how did the answer land? Was
     there a real STAR arc with a concrete Result, or did it trail off? Did the user
     reach for the story the prep mapped, or grab a weaker one?
   - **Gap handling** — which logged gaps got probed, and did the prepared framing hold
     up under follow-up, or crumble?
   - **Signal from the other side** — where the interviewer leaned in, pushed back, went
     quiet, or redirected. Note it without over-reading a transcript.
3. **Deliver a tight learning report**, not a transcript re-narration:
   - the 2–3 answers that landed strongest (and why, so they're repeatable);
   - the 2–3 highest-leverage fixes, each tied to a specific moment in the transcript
     and a concrete reshaping — what to say instead next time;
   - any story that underperformed and how to rebuild it (from real material only);
   - questions the prep missed, so they go into the bank.
   Keep it honest and specific. Praise what genuinely worked; don't manufacture
   encouragement, and don't pile on — the point is the next interview, not a grade.

## Enriching the library from a debrief

Per "The library is a living system," the debrief writes back the most valuable updates
the kit ever makes, because they're grounded in real performance:

- **Underperforming stories** → flag in `fact-pack.md` for reshaping, with a note on
  *why* it didn't land (no clear result, too long, wrong emphasis).
- **Unpredicted questions** → add to the predicted-question patterns so future prep for
  similar roles anticipates them.
- **Gap-framings that failed** → rewrite the framing in the gap notes so next time it
  holds.
- **A genuinely strong answer** → capture the version that worked, so it's reusable.

Record only what the transcript actually supports — never infer a fact about the user to
fill a gap. Apply the user's `library_enrichment.mode` (confirm vs. silent) as
everywhere else. Over a job search, this is what turns the kit from a static helper into
a system that measurably gets better at getting *this user* through interviews.
